### 1. Общие сведения

**1.1. Назначение**  
Настоящий документ предназначен для владельца / администратора приложения «TopMessenger». Описаны принципы работы, настройка серверной части, управление данными пользователей и мониторинг.

**1.2. Состав комплекса**

- Мобильное клиентское приложение (Flutter, Android / iOS).
    
- Серверная часть (Django + WebSocket).
    
- База данных (SQLite / PostgreSQL).
    
- API-эндпоинты (REST) и WebSocket-соединения.
    

**1.3. Адрес сервера по умолчанию**  
`http://91.214.78.192`  
`ws://91.214.78.192`

### 2. Требования к среде администрирования

- Доступ к серверу по SSH / консоли.
    
- Установленные: Python 3.10+, Django 4+, база данных.
    
- Открытые порты: 80 (HTTP), 443 (HTTPS — опционально), 8000 (WebSocket).
    
- Средство просмотра логов (journalctl / tail).

### 3. Управление серверной частью

**3.1. Запуск и остановка**

bash

# Запуск сервера Django (production — через gunicorn + daphne для WebSocket)
daphne -b 0.0.0.0 -p 8000 your_project.asgi:application
# Остановка
pkill -f daphne

**3.2. Проверка работоспособности**

- API-статус: `GET http://91.214.78.192/` → код ответа < 500.
    
- WebSocket: подключение к `ws://91.214.78.192/dialogs/ws/{id}?token={token}`.
    

**3.3. Обновление серверной логики**

1. Загрузить новый код на сервер.
    
2. Применить миграции БД:
    
    bash
    
    python manage.py migrate
    
3. Перезапустить ASGI-сервер.

### 4. Управление пользователями

**4.1. Просмотр зарегистрированных пользователей**  
Через админ-панель Django:  
`/admin` → модель `User` / `Profile`.

**4.2. Блокировка / удаление**

- Блокировка: установить флаг `is_active = False`.
    
- Удаление: удалить запись из БД (каскадно — все сообщения и контакты).
    

**4.3. Сброс пароля пользователя**  
Через админ-панель или командой:

bash

python manage.py changepassword <username>

---

### 5. Токены и сессии

**5.1. Формат авторизации**  
`Authorization: Bearer <access_token>`

**5.2. Время жизни токена**

- Передаётся в поле `expires_in` при логине (обычно 1–24 часа).
    
- Серверный метод `_refreshToken()` в текущей версии не реализован — после истечения токена требуется повторный вход.
    

**5.3. Принудительный выход пользователя**  
Удалить токен из БД (если токены хранятся) или сменить секретный ключ JWT (при использовании JWT).

### 6. Мониторинг и логи

**6.1. Логи API-запросов**

- В консоли сервера выводятся: метод, URI, статус ответа, тело (при наличии).
    
- Пример:
    
    text
    
    POST http://91.214.78.192/auth/login -> 200
    

**6.2. Логи WebSocket**

- Подключения, сообщения, ошибки, закрытия.
    
- Выводятся в консоль сервера в реальном времени.
    

**6.3. Ошибки клиента**  
Клиент присылает (если настроено) или администратор видит в логах сервера:

|Код|Значение|
|---|---|
|401|Неавторизован / токен истёк|
|404|Ресурс не найден|
|500|Ошибка сервера|

### 7. Безопасность

**7.1. Рекомендации**

- Использовать HTTPS для production.
    
- Хранить секретный ключ в переменных окружения, не в коде.
    
- Ограничить CORS только доверенными доменами.
    
- Включить rate limiting (на сервере — дополнительно к клиентскому).
    

**7.2. Обработка ошибок аутентификации**  
При 401 клиент автоматически очищает токен и перенаправляет на экран логина.

### 9. Частые проблемы и их решение

|Проблема|Решение|
|---|---|
|Клиент не подключается к WebSocket|Проверить, запущен ли `daphne` и открыт ли порт|
|Токен не принимается|Убедиться, что в заголовке `Authorization` нет лишних пробелов|
|Сообщения не доставляются|Проверить `contactId` и права доступа между пользователями|
|Контакт не добавляется|Убедиться, что email существует и пользователь не добавляет сам себя|
